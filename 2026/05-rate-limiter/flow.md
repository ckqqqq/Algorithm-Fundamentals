# 提问
Token 计数限流：每用户每分钟最多 N 次请求、M 个 token，设计数据结构和 API。（滑动窗口 / 环形数组）

. 从最笨的方案开始（正常人都会先想到）
# 直觉版：队列里存每条请求
queue: deque[(timestamp, tokens)]
每次请求: 弹出时间 < now-60 的记录, 再求和判断
精确、好懂，但内存 O(QPS × 60)，高并发撑不住。它的价值是当"正确性基线"——后面所有优化都要保持它的语义（窗口内合计）。
3. 意识到我们不需要每条记录，只需要"合计"
既然只关心窗口内总数，那把 60 秒切成 60 个 1 秒桶，每桶只存两个整数（请求数、token 数）。这就是你的第一版 CircularArrayLimiter 的思路——它没错，只是每次请求都把 60 个桶加一遍，O(桶数) 求和。精度上最多差一个桶的量，属于"近似滑动窗口"，桶越细越准。
4. 为什么是环形数组
时间只往前走，桶编号 = (now // 桶长) % 桶数，会循环。旧桶的位置正好被新桶覆盖，数组不用移动、不用删，天然复用。关键设计：每个桶必须存 timestamp，否则没法区分"这个位置的桶是哪个周期的"。
5. O(桶数) → O(1)：维护窗口累计值
你的第二版 OptimizedCircularLimiter 方向是对的：维护 window_requests / window_tokens，复用旧桶时"减旧"，写入时"加新"。但这里有两个坑，是这题真正的考点：
空闲恢复：如果只做"复用当前桶时减旧"，那么突刺/空闲后，环里会残留"还没轮到复用、但其实已经过期"的桶，累计值不减 → 误拒。你的代码里 ... 省略的部分必须包含清扫逻辑，或者发现间隔 ≥ 一个窗口就整体清零。
复用判定：当 bucket.ts != bucket_ts 时，在"ring 恰好覆盖一个窗口"的设计下，被复用的桶一定是一个窗口前的 → 一定过期 → 先减后写是对的。
6. 每用户一份
dict[user_id] -> limiter，惰性创建。坑：dict 只增不减，生产会内存泄漏，要加 TTL/LRU 清理；多机部署就用 Redis + Lua 原子脚本（ZSET 或 INCR）。
